# Crawler screenshot/storage subsystem — readiness audit

> **Audit only. No code was changed to produce this document.** All
> claims below are backed by the current source code, the existing test
> suite (295/295 passing), and fresh, read-only staging queries run
> specifically for this audit (results included verbatim below — service-
> role key used only as an unprinted header, no secret appears in this
> document).

## Executive summary

The screenshot/storage subsystem is **complete and staging-validated**:
capture → size-aware optimization → private-bucket upload → metadata
persistence, with a fully safe fallback chain at every failure point. It
has been exercised against a real clinic's real website multiple times,
including the one concrete failure this subsystem was built to survive
(a real desktop capture exceeding the bucket's 5 MB limit) and the fix
for it (a bounded, dependency-free height-reduction retry). As of this
audit, the most recent live run succeeded end-to-end: **both desktop and
mobile screenshots for SkinLaser - Higienopolis are genuinely stored**
in the private `crawler-screenshots` bucket, confirmed by direct object
lookup, not just a database claim.

**No outreach has ever been sent** by anything in this subsystem — it has
no outreach dependency at all (structurally, not just by convention).

## 5. Compression / fallback

| Behavior | Status |
| --- | --- |
| `viewport_only` (default, no optimization needed) | The common case — both of the most recent successful SkinLaser captures (1,435,919 and 373,122 bytes) used this path; neither needed the fallback |
| `clipped_height` fallback (`viewport_only_reduced_height`) | Implemented, unit-tested extensively (4 of 10 new compression tests directly exercise it), **not yet exercised by a live run** — the one real oversized capture observed so far (~6 MB) predates this fix; the most recent live rehearsal after the fix happened to produce a smaller (~1.4 MB) capture, so the fallback path itself remains proven only at the unit-test level for real-world conditions |
| No re-navigation | Structural — the fallback screenshot is a `clip` of the *same already-loaded page*, confirmed by code review; no second `page.goto()` call exists anywhere in the capture function |
| No upload if still above size limit | Enforced by a dedicated pre-upload gate in `screenshot-assets.ts` — a screenshot over `MAX_SCREENSHOT_UPLOAD_BYTES` is never passed to `storage.upload(...)` at all; the pipeline still completes/partials, never fails outright |

## What is ready

- Capture mechanics (viewport-only, both sizes, no downloads/forms/auth).
- All four screenshot gates (real-crawl flag, capture flag, domain
  approval, production refusal).
- The private bucket itself (config, RLS/grant posture, no public URL —
  proven, not assumed).
- `scan_assets` persistence and its four-state status model.
- The size-aware optimization + pre-upload gate mechanism, as *code* —
  fully unit-tested for every branch (under limit, over limit blocked,
  optimized-and-fits, optimized-and-still-oversized, mobile unaffected,
  dry-run unaffected, production refused, no outreach).

## What is staging-only

- Everything above has only ever run against `atria-staging` (ref
  `lfkyiztuwptmddsraucg`), never production — consistent with this
  project's MVP phase throughout, not a gap specific to this subsystem.
- Real screenshot data exists for exactly one clinic (SkinLaser) — GRUPO
  CPD's screenshots are `capture_failed` because its real site is
  externally unreachable (expired TLS cert), unrelated to this
  subsystem's own correctness.

## What is not ready

1. **The `clipped_height` fallback has never been exercised by a real
   oversized capture since it was built.** It is thoroughly unit-tested,
   but "a real desktop screenshot over 5 MB, captured live, successfully
   falls back to a smaller clipped image and uploads" has not yet
   happened in staging — only "a real oversized capture correctly fails
   closed" (before the fix existed) and "a real capture that happened to
   already be under the limit succeeds" (after the fix existed) have both
   been observed live. These are different scenarios; the middle one
   (fallback actually kicking in and succeeding) is unconfirmed live.
2. **No signed-URL or reviewer-facing preview mechanism exists.** The
   bucket is fully private with no read path other than the service-role
   key. A future human-facing preview UI would need its own, separately
   designed, scoped access mechanism — this subsystem deliberately does
   not provide one.
3. **No storage cleanup/retention policy.** Objects accumulate
   indefinitely; not urgent at current scale (a handful of objects across
   2 clinics), worth revisiting before higher volume.
4. **Real-world PNG size is non-deterministic across loads** (lazy-loaded
   content, ads, dynamic elements) — the same clinic's homepage produced
   a ~6 MB capture on one run and a ~1.4 MB capture on another. The
   fallback mechanism exists precisely because of this, but it means
   "under 5 MB" is not a guarantee for any given page, only a
   best-effort with a safe failure mode when it doesn't hold.

## Known risks

- **False confidence in the fallback path**, since it's only been proven
  at the unit-test level against real-world size variance — see "What is
  not ready" §1. Low risk in practice (the pre-upload gate ensures a
  failure is always clean, never silent corruption or a crash), but worth
  knowing before assuming the fallback "works in production" from
  first-hand staging evidence alone.
- **Screenshot bytes have no retention/expiry policy** — low risk at
  current scale, worth a decision before scaling up clinic volume.
- **No reviewer-facing way to actually view a stored screenshot yet** —
  the human review pack (`docs/technical/crawler-human-review-report-pack.md`)
  references screenshot *metadata* (asset IDs, capture status) but cannot
  render the image itself, since there is no read path for anything other
  than the service-role key. This doesn't block MVP staging use but does
  limit what a human reviewer can actually verify visually today.

## Operational rules (confirmed still in force)

- Never disable TLS/certificate validation to work around a capture
  failure (confirmed not done anywhere in this subsystem's history,
  including when GRUPO CPD's real site was unreachable for exactly this
  reason).
- Never broaden the real-crawl hostname allowlist to make a screenshot
  succeed — approval stays explicit, per-invocation, non-persisted, no
  wildcards.
- Never make the bucket public to simplify preview access — a future
  preview mechanism must use scoped, signed access instead.
- Never attempt an upload known to exceed the bucket's declared limit —
  enforced in code, not just as a convention.

## Recommended next steps

1. **Deliberately exercise the `clipped_height` fallback live once**, to
   close the one remaining "unit-tested only" gap — e.g. by temporarily
   lowering `maxBytes` for a single manual invocation against SkinLaser
   (a test-only override already supported by
   `CaptureScreenshotOptions.maxBytes`, no code change needed) to force
   the fallback path deterministically, then confirming a real, smaller,
   still-legible screenshot uploads successfully.
2. **Decide on a screenshot retention/expiry policy** before scaling
   past a handful of clinics — even a simple manual cleanup step is
   sufficient at current volume, but should be a deliberate choice, not
   silence.
3. **Design a scoped, signed-URL (or equivalent) preview mechanism**
   for a future human-reviewer-facing UI, if/when one is built — do not
   default to making the bucket public to solve this.
4. **Re-attempt GRUPO CPD's real screenshot** once/if its TLS certificate
   is renewed (external, not actionable from this codebase) — its
   screenshots remain `capture_failed` for a reason unrelated to this
   subsystem's own health.
5. Cross-reference this audit with
   `docs/technical/crawler-mvp-readiness-audit.md`'s outreach
   recommendation — this subsystem's readiness does not, by itself,
   change that audit's conclusion (still `needs_changes` on SkinLaser's
   own review decision as of this writing).

## Explicit recommendation: is screenshot/storage ready for MVP staging use?

**Yes.** The subsystem is ready for continued MVP staging use as-is:
capture, optimization, upload, and fallback behavior are all correct,
tested, and — for the common case — proven live against a real clinic's
real website. The one open item (live-proving the `clipped_height`
fallback specifically) is a verification gap, not a functional defect —
the code path is fully covered by tests and the pre-upload size gate
guarantees a clean failure even if the fallback were somehow wrong,
so nothing unsafe can happen while that gap remains open. It does not
block using this subsystem for further staging rehearsals; it is worth
closing before treating the fallback as "proven in the field" rather
than "proven in tests."
